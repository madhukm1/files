# Big Picture First (VERY IMPORTANT)

Before going into the 9 steps, understand this one sentence:

> **Designing a clocked sequential circuit = converting BEHAVIOR into HARDWARE**

Behavior is given as:

* state diagram
* timing diagram
* word problem

Hardware means:

* flip-flops
* logic gates
* clock

These **9 steps** are simply a **systematic way to do that conversion**.

---

# What are we designing?

You are given:

* a **state diagram**
* one input `X`
* one output `Y`
* circuit must be **clocked**
* uses **flip-flops**

Goal:

> Build a real circuit that behaves exactly like the given state diagram.

---

# STEP 1️⃣ — Given State Diagram / Timing Diagram

### What does this mean?

Someone already told you:

* how the system behaves
* how states change
* when output is 0 or 1

This is **WHAT** the circuit should do — not **HOW**.

👉 This is common in real life:

* protocol description
* controller spec
* datasheet behavior

So step 1 is just:

> “Understand the behavior”

No hardware yet.

---

# STEP 2️⃣ — Obtain the State Table

Now we **translate the picture into a table**.

### Why?

Because **tables are easier to work with mathematically**.

### State Table contains:

1. Present State (PS)
2. Input
3. Next State (NS)
4. Output

### Present State

You used:

```
QA QB
```

Because:

* 2 flip-flops
* each flip-flop stores 1 bit
* together they represent the state

### Why QA QB?

Because **state lives inside flip-flops**.

---

### Next State

For each present state:

* check what happens when `X = 0`
* check what happens when `X = 1`

From the **state diagram arrows**, you fill:

```
QA+ QB+
```

---

### Output

From the diagram:

* write output corresponding to each transition

Now you have **complete behavior in table form**.

👉 This table is the **heart of the design**.

---

# STEP 3️⃣ — State Reduction (If Possible)

### Why reduce states?

* fewer states → fewer flip-flops → simpler circuit

### When can states be reduced?

Two states can be merged **only if**:

* for all inputs → next states are same
* outputs are same

In your case:

* no two states behave identically
  ➡ **no reduction possible**

That’s completely fine.

Most real FSMs **cannot be reduced**.

---

# STEP 4️⃣ — State Assignment (Binary Coding)

Sometimes states are named:

```
A, B, C, D
```

But flip-flops understand only **0 and 1**.

So we assign:

```
A = 00
B = 01
C = 10
D = 11
```

This is called **state assignment**.

👉 In your example, this was **already done**, so you skipped it.

---

# STEP 5️⃣ — Determine Number of Flip-Flops

Rule:

```
Number of flip-flops = ⌈log₂(number of states)⌉
```

Here:

* 4 states
* log₂(4) = 2
  ➡ need **2 flip-flops**

You named them:

* Flip-flop A → QA
* Flip-flop B → QB

Perfect.

---

# STEP 6️⃣ — Choose Flip-Flop Type (Implicit Step)

You chose:

* **T flip-flops**

This is important because:

* different flip-flops need different excitation logic

In real designs:

* usually D flip-flops
* but learning T is excellent for understanding

---

# STEP 7️⃣ — Circuit Excitation Table (MOST IMPORTANT STEP)

This is where **behavior becomes logic**.

### What is excitation table?

It answers:

> “What input must I give to the flip-flop to move from present state to next state?”

You listed:

* Present state (QA QB)
* Input X
* Next state (QA+ QB+)

Now you must find:

* TA (input to flip-flop A)
* TB (input to flip-flop B)

---

### Using T Flip-Flop Rule

For T flip-flop:

```
T = Q ⊕ Q+
```

Meaning:

* if state doesn’t change → T = 0
* if state toggles → T = 1

This is **golden rule**.

So:

* compare QA with QA+
* compare QB with QB+
* XOR them

That’s why you correctly said:

> “T is odd-ones detector”

Excellent intuition 👍

---

# STEP 8️⃣ — Obtain Boolean Expressions

Now you have:

* table showing when TA = 1
* table showing when TB = 1
* table showing when Y = 1

From this:

* write Boolean expressions
* optionally minimize using K-map

You did:

* TA = function(QA, QB, X)
* TB = function(QA, QB, X)
* Y = function(QA, QB)

This step produces **real logic equations**.

---

# STEP 9️⃣ — Implement the Circuit

Now everything is ready.

You build:

* 2 T flip-flops
* combinational logic for TA and TB
* combinational logic for Y
* connect clock to flip-flops

🎉 **Design complete**

# How This Is Used in TOP-LEVEL DESIGN (VERY IMPORTANT)

In real systems:

* USB controller
* NAND flash controller
* CPU control unit
* FX3 firmware FSM

Engineers follow **same flow**, just with tools.

### Tool flow:

1. Write state diagram (mentally or on paper)
2. Write FSM in HDL
3. Synthesis tool does steps 7–9 automatically

### HDL version of same idea:

```verilog
always @(posedge clk)
  state <= next_state;

always @(*)
  next_state = function(state, input);
```

# 1️⃣ First: Why do we need “models” at all?

When we design **synchronous sequential circuits**, we already know:

* There is **memory** (flip-flops)
* There is **combinational logic**
* There is a **clock**
* There are **inputs**
* There are **outputs**

But here is the key question:

> **WHEN should the output change?**

That single question creates **two different design models**.

That’s it.
Everything about Moore vs Mealy comes from this one idea.

---

# 2️⃣ The two models (names first, meaning later)

There are **only two models**:

1. **Moore State Machine**
2. **Mealy State Machine**

They are **not different circuits fundamentally**.
They differ **only in output generation**.

Let me repeat this very clearly:

> 🔑 **Moore and Mealy differ ONLY in how the output is generated**

---

# 3️⃣ Basic structure of any sequential circuit

Every synchronous sequential circuit has **three blocks**:

```
INPUT ──► Next-State Logic ──► Flip-Flops ──► Present State
                               │
                               ▼
                         Output Logic
```

So we always have:

* **Next-state logic**
* **Memory (flip-flops)**
* **Output logic**

The difference between Moore and Mealy is:
👉 **What signals are given to the output logic**

---

# 4️⃣ Moore State Machine (MOST IMPORTANT FIRST)

### Definition (simple words)

> In a **Moore machine**,
> **output depends ONLY on the present state**

That means:

```
Output = f(Present State)
```

❌ Output does NOT depend directly on input
❌ Input cannot immediately change output

---

## 4.1 Block-diagram understanding (very important)

In a Moore machine:

* Input goes only to **next-state logic**
* Output logic takes input **only from flip-flops**

```
Input ──► Next State Logic ──► Flip-Flops ──► Output Logic ──► Output
```

There is **NO direct path** from input to output.

This is the key visual test.

---

## 4.2 What does this mean in real life?

Imagine a traffic light controller 🚦

* Red, Yellow, Green are **states**
* Output (light color) depends on **current state only**
* Pedestrian pressing button does NOT instantly change light
* Button affects **next state**, not output immediately

👉 This is a **Moore machine**

---

# 5️⃣ How to identify a Moore machine from a circuit

Ask **one question**:

> Does the output expression contain the input?

If:

```
Y = f(QA, QB)
```

✔ Moore machine

If:

```
Y = f(QA, QB, X)
```

❌ Not Moore

---

## 5.1 Your example (why it is Moore)

You derived:

```
Y = QB̅ + QA
```

Notice:

* QA → flip-flop output
* QB → flip-flop output
* ❌ No input `A` in the equation

So:

> Output depends ONLY on present state
> ✔ Moore State Machine

---

# 6️⃣ Moore State Diagram (VERY IMPORTANT VISUAL CHANGE)

### In Moore machines:

* Output is associated with **state**
* Not with transitions

### So we write output:

👉 **inside the state bubble**

Example:

```
[S0 / Y=0]
[S1 / Y=1]
```

Transitions show:

* **only input**

```
S0 --(X=1)--> S1
```

No output written on arrows.

---

## 6.1 Why output is written inside the state?

Because:

* Output remains constant
* As long as the machine stays in that state

Output changes **only when state changes**
→ which happens **only on clock edge**

---

# 7️⃣ Why Moore machines are popular in real design

### Advantages:

✔ Outputs are stable
✔ No glitches
✔ Easy timing analysis
✔ Safe for hardware

### Disadvantages:

❌ Sometimes need more states
❌ Output reacts one clock later

In **FPGA/ASIC design**, Moore machines are **preferred** for safety.

---

# 8️⃣ How Moore machines are used in top-level design

### Typical examples:

* CPU control unit
* NAND Flash command FSM
* USB controller
* UART controller
* Traffic light controller

Engineers like Moore machines because:

> **Output changes only at clock edge → predictable**

# 9️⃣ How Moore looks in HDL (important intuition)

```verilog
always @(posedge clk)
  state <= next_state;

always @(*)
  case(state)
    S0: Y = 0;
    S1: Y = 1;
  endcase
```

Notice:

* Output depends only on `state`
* No input in output logic

That is **pure Moore**.

# 1️⃣ First, recall ONE key sentence (anchor)

You already learned this, but let’s lock it in:

- **Moore machine** → Output depends on **present state only**
- **Mealy machine** → Output depends on **present state AND input**

That single difference explains **everything** that follows.

---

# 2️⃣ Why Mealy machines exist at all

Engineers asked:

> “Why should I wait for a clock edge to change output  
> if the input already tells me what to do?”

That question led to **Mealy machines**.

So Mealy machines are about:
- **faster response**
- **fewer states**
- **more compact design**

---

# 3️⃣ Internal structure: Moore vs Mealy (mental picture)

## Moore structure (you already know)
```
Input ──► Next State Logic ──► Flip-Flops ──► Output Logic ──► Output
```
Output logic sees:
- ✔ Present state
- ❌ Input

---

## Mealy structure (small but important change)
```
Input ──► Next State Logic ──► Flip-Flops
   │                                 │
   └────────────► Output Logic ◄─────┘
```

Output logic sees:
- ✔ Present state
- ✔ Input

That’s the **only structural difference**.

---

# 4️⃣ Definition in simple language

> In a **Mealy state machine**,  
> output can change **immediately** when input changes  
> (even without waiting for a clock edge).

Mathematically:
```
Output = f(Present State, Input)
```

---

# 5️⃣ How to IDENTIFY a Mealy machine (very practical)

Ask just one question:

> Does the output expression include the input?

### Example you derived:
```
Y = QB̅ + QA + A
```

Here:
- QB̅ → state
- QA → state
- **A → input**

✔ Input is involved  
➡ **Mealy machine**

This is the fastest way to identify Mealy vs Moore in exams and interviews.

---

# 6️⃣ State diagram difference (VERY IMPORTANT)

This is where students usually get confused — so let’s go slowly.

## Moore state diagram
- Output written **inside state**
- Arrow shows **only input**

```
[S0 / 0] --(X=1)--> [S1 / 1]
```

---

## Mealy state diagram
- Output written **on transition**
- Arrow shows **input/output**

```
S0 --(X=1 / Y=0)--> S1
```

### Memory trick:
> **Mealy = output on arrow**

---

# 7️⃣ Why output is written on arrow in Mealy

Because:
- Output depends on input
- Input is applied **during transition**
- So output is associated with that transition

In Moore:
- Output is fixed for entire state

In Mealy:
- Output can change **even if state does not change**

---

# 8️⃣ Your example explained intuitively

You modified the previous circuit by adding input `A` to the output OR gate.

Now:
- Same state
- Different input
- Different output

That is **pure Mealy behavior**.

Meaning:
> “I don’t need to wait for next clock edge to decide output.”

---

# 9️⃣ Why Mealy machines use FEWER states

This is an **important design insight**.

### Moore machine:
- Output tied to states
- If output changes → often need new state

### Mealy machine:
- Output tied to input + state
- Can reuse same state
- Output changes via input

➡ **Mealy machines usually need fewer states**

That’s why your teacher said:
> “Implementation of same logic requires fewer states in Mealy”

---

# 🔟 Trade-off: Moore vs Mealy (REAL DESIGN VIEW)

| Feature | Moore | Mealy |
|------|------|------|
| Output timing | Changes on clock | Can change immediately |
| Stability | Very stable | Can glitch |
| States | More | Fewer |
| Hardware safety | High | Medium |
| Speed | Slightly slower | Faster |

---

# 1️⃣1️⃣ Where Mealy machines are used in real systems

Mealy machines are used when:
- **fast reaction is required**
- **input-driven outputs**

Examples:
- Sequence detectors
- Communication protocols
- Handshake signals
- Control signals like READY/VALID
- Some NAND Flash interface logic

---

# 1️⃣2️⃣ Example from real life (simple analogy)

### Moore-like behavior:
Traffic light 🚦  
Light changes only when timer expires.

### Mealy-like behavior:
Automatic door 🚪  
Door opens **immediately** when sensor detects you.

No waiting.

---

# 1️⃣3️⃣ HDL intuition (VERY IMPORTANT)

### Mealy-style output logic
```verilog
always @(*)
  case(state)
    S0: Y = X & enable;
    S1: Y = ~X;
  endcase
```

Here:
- Output depends on **state and input**
✔ Mealy

---

# 1️⃣4️⃣ Common beginner confusion (important warning)

❗ Mealy outputs may **glitch** if input is noisy  
Because:
- output changes without clock synchronization

That’s why:
- Moore → safer
- Mealy → faster but needs care

In real designs:
- Often a **hybrid approach** is used

---

# 1️⃣5️⃣ How this fits into TOP-LEVEL DESIGN thinking

When designing FSMs, engineers ask:

1. Do I need fast output response?
   - YES → Mealy
   - NO → Moore

2. Is output safety critical?
   - YES → Moore
   - NO → Mealy

3. Can I tolerate glitches?
   - YES → Mealy
   - NO → Moore

---

# 1️⃣6️⃣ One-line comparison (MEMORIZE THIS)

> **Moore = state decides output**  
> **Mealy = state + input decides output**

- They are just **more responsive**
- Output can change **between clocks**
- They often need **fewer states**
- But they need **careful design**
